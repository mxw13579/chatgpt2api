# 1.9.6 存储、日志与进度保留

本次优化与图片 API 兼容改造一起发布，默认仍运行单个应用进程，不需要数据库 schema 迁移。

## 账号增量持久化

- 日常账号更新、使用时间、图片额度结果、失效删除及 token 轮换，通过 `apply_account_changes(upserts, deleted_tokens)` 仅查询/修改涉及的键。
- PostgreSQL / SQLite / MySQL 的数据库实现不会为单账号变化读取整个账号表；每批最多处理 400 个键，所有批次同一事务提交。轮换旧 token 的删除与新 token 的写入保持原子性。
- 持久化成功后才更新内存账号、别名及并发槽位；失败不静默降级成全量重试，也不在异常中输出 SQL 参数或凭据。
- `save_accounts()` 仍保留全量快照同步语义，供导入、恢复等需要全量同步的调用使用。
- JSON/Git 后端兼容原来的全量文件保存方式；本次数据库读取量优化不等于 JSON/Git 文件也获得了行级存储。

## 业务日志

`data/logs.jsonl` 默认每 **16MiB** 轮转，保留 **5 个备份**：

```text
logs.jsonl       当前分片
logs.jsonl.1     最新备份
...
logs.jsonl.5     最旧保留备份
```

- 查询从尾部按块读取，默认最多返回 200 条；类型和日期过滤会继续搜索保留分片，不仅查询当前文件。
- 旧的超大日志在下一次写入时整体移入备份，不在启动时全量拆分；因此升级初期可能暂时超过常规约 96MiB 的总量，之后按分片保留策略淘汰。
- 单条超过轮转阈值的日志不截断；超过默认 1MiB 查询上限的超长行保留在文件，但不在列表中解析返回。
- 倒读查询、追加、轮转、删除在同一 `LogService` 实例内线程互斥；删除流式重写并原子替换，保留未选记录。
- 现有显式日志 ID 保持不变；没有 ID 的旧记录采用新的稳定标识方式，升级前已打开的日志页面应刷新再删除。
- 日志查询及删除在线程池运行，避免在异步路由中执行整段文件 I/O。
- 生产使用单个 `LogService` 实例，锁只协调该实例的多线程访问，不提供同路径多实例或多进程互斥。不要直接启动多个 worker 共同写同一个日志文件；多进程部署需要另行设计共享日志收集和账号状态协调。

业务日志和 Docker stdout 日志是两套独立保留机制。建议为 Compose 的 `app` 服务配置 Docker 日志轮转，例如：

```yaml
logging:
  driver: json-file
  options:
    max-size: "20m"
    max-file: "3"
```

这需要重建应用容器才能生效，不需要重建 PostgreSQL。历史日志如需长期审计，应先独立备份，不要依赖运行时分片永久保留。

## 刷新及重新登录进度

- 两类进度合计最多 **128 条**，记录在任务提交前预留。
- 达到上限时返回 HTTP **429**，不会先启动后台任务再丢弃其进度。
- 完成后保留 **30 分钟**，在创建、查询和更新进度时清理；活跃记录不会因 TTL 被误删。
- 缓存仅保留计数、脱敏错误和结果摘要，不保留整池历史账号快照。为兼容原接口，完成结果中的 `items` 在查询时读取当前账号列表，因此不是完成时的历史快照。
- 过期或不存在的进度查询仍返回 404。客户端应重新加载账号列表，而不是无限轮询过期 ID。
- 日志磁盘故障不会把已成功刷新的账号误标异常；必要的完成进度更新不依赖日志写入成功。

## 发布与回滚

1. 备份 Compose、运行时配置、数据库及需要保留的日志/任务索引；备份包含敏感信息，必须限制权限。
2. 保留旧镜像，按新镜像的不可变 digest 更新 `app` 服务；保留现有端口、卷、代理及 PostgreSQL 配置。
3. 检查版本、接口健康、数据库错误，以及至少一轮后台刷新期间的全表扫描和网络增量。
4. 需要回滚时恢复旧应用镜像即可，无需为本次改造执行 schema 回退。旧应用只认识 `logs.jsonl`，不会自动展示 `.1` 等历史分片；这些分片仍在磁盘，不要当成日志丢失。

镜像使用空的初始 `config.json`；生产配置仍通过既有挂载或环境变量提供，不会随镜像发布。真实画图成功率仍依赖账号、网络和上游，本次离线协议测试不代替真实上游验收。
